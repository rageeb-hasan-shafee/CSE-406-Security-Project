\section{Introduction}

TCP Window Scale is used to allow TCP connections to work with
windows larger than the normal 16-bit TCP window. The scale value
is negotiated during the initial TCP handshake using the SYN and
SYN-ACK packets.

In this project, we studied what happens when an on-path attacker
changes the Window Scale value in the client's SYN packet. The main
idea is simple: if the client and server use different Window Scale
values, they can have different ideas about the actual receive window.

We tested three attacks:

\begin{enumerate}
    \item \textbf{Deflate:} change the client's Window Scale from
    10 to 0. The server then thinks the client's window is much smaller.

    \item \textbf{Inflate:} change the client's Window Scale to 14.
    The server then thinks the client's window is much larger than
    the client's real receive buffer.

    \item \textbf{Slow Read / Zero-Window DoS:} do not modify packets.
    Instead, keep many connections open and read data very slowly.
\end{enumerate}

We also tested three defenses:

\begin{enumerate}
    \item Static ARP entries
    \item IPsec AH
    \item A live Window Scale mismatch detector
\end{enumerate}

For each experiment, we compare what we expected with what actually
happened.

\section{TCP Window Scale in Simple Terms}

The TCP receive window contains a 16-bit advertised value. Window
Scale allows this value to represent a much larger window.

The effective window can be written as:

\[
\text{Effective Window}
=
\text{Advertised Window}\times 2^{\text{Window Scale}}
\]

For example, with Window Scale 10:

\[
2^{10}=1024
\]

So the advertised window is multiplied by 1024.

The important point for this project is that the Window Scale value
is negotiated during the initial handshake.

\begin{figure}[h]
\centering
\begin{tikzpicture}[node distance=1.4cm]

\node[box] (client) {Client};
\node[box,right=4cm of client] (server) {Server};

\draw[arrow] (client) -- node[above,align=center]
{SYN\\WScale = 10} (server);

\draw[arrow] (server) -- node[below,align=center]
{SYN-ACK\\WScale = 10} (client);

\node[smallbox,below=1.6cm of client] (window)
{Advertised Window\\$\times 2^{10}$};

\node[smallbox,below=1.6cm of server] (result)
{Both sides agree\\on the scale};

\draw[dashedarrow] (client) -- (window);
\draw[dashedarrow] (server) -- (result);

\end{tikzpicture}
\caption{Normal TCP Window Scale negotiation}
\end{figure}

An attacker who changes the Window Scale value in the SYN can make
the server use a different scale from the one actually used by the
client.

\section{Attack 1: Deflate}

\subsection{Idea}

In the deflate attack, the attacker changes the client's Window Scale
from 10 to 0.

The Window Scale calculation is:

\[
\text{Effective Window}
=
\text{Advertised Window}\times 2^{\text{Window Scale}}
\]

Therefore, changing the scale from 10 to 0 makes the server believe
that the client's window is

\[
2^{10}=1024
\]

times smaller than it really is.

\subsection{Deflate Attack Diagram}

\begin{figure}[h]
\centering
\begin{tikzpicture}[node distance=1.5cm and 1.4cm]

\node[box] (client) {Client\\Real WScale = 10};
\node[box,right=2.6cm of client] (attacker) {Attacker\\Changes 10 $\rightarrow$ 0};
\node[box,right=2.6cm of attacker] (server) {Server\\Sees WScale = 0};

\draw[arrow] (client) -- node[above,align=center,font=\footnotesize]{Original SYN\\WScale = 10} (attacker);
\draw[arrow] (attacker) -- node[above,align=center,font=\footnotesize]{Modified SYN\\WScale = 0} (server);

\node[smallbox,below=1.6cm of server] (belief)
{Server thinks window\\is 1024$\times$ smaller};

\node[smallbox,below=1.6cm of client] (result)
{Real client window\\is much larger};

\draw[dashedarrow] (server) -- (belief);
\draw[dashedarrow] (client) -- (result);

\end{tikzpicture}
\caption{Deflate attack: Window Scale is reduced from 10 to 0}
\end{figure}

\subsection{Attack Process}

The experiment was performed in the following steps.

\begin{enumerate}
    \item First, a normal 20 MB transfer was performed without an attacker.
    This gave us the baseline result.

    \item ARP spoofing was started so that the attacker could stay
    between the client and server.

    \item IP forwarding was enabled on the attacker.

    \item TCP SYN packets were sent to NFQUEUE using:

\needspace{8\baselineskip}
\begin{lstlisting}
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN SYN \
    -j NFQUEUE --queue-num 0 --queue-bypass
\end{lstlisting}

    \item \texttt{wscale\_attack.py} inspected the client's SYN packet
    and changed its Window Scale from 10 to 0.

    \item The same 20 MB transfer was performed again.

    \item Finally, the packet capture was checked using the detector
    script and Wireshark.
\end{enumerate}

\subsection{Expected Result}

We expected the server to believe that the client's receive window
was much smaller than its actual window.

Because the scale changed from 10 to 0, the server should limit its
sending rate heavily.

We therefore expected a large throughput reduction without a large
number of retransmissions.

\subsection{Actual Result}

The attack successfully changed the Window Scale:

\needspace{10\baselineskip}
\begin{lstlisting}
2026-09-19 00:20:48,239 listening on NFQUEUE 0
2026-09-19 00:20:50,989 rewrote WScale
10.0.0.1:44992 -> 10.0.0.2:9000
shift 10 -> 0
\end{lstlisting}

The measured results were:

\begin{table}[h]
\centering
\begin{tabular}{lrrrr}
\toprule
Run & Throughput (MB/s) & Retransmissions & RTT ($\mu$s) & WScale \\
\midrule
Baseline & 1781.163 & 0 & 360 & 10 \\
Deflate  & 2.314    & 0 & 9   & 0 \\
\bottomrule
\end{tabular}
\caption{Deflate attack results}
\end{table}

The throughput dropped by about 99.9\%.

There were no retransmissions. This shows that the slowdown was caused
by TCP flow control and the incorrect Window Scale value, rather than
packet loss.

The packet detector also found the expected mismatch:

\needspace{13\baselineskip}
\begin{lstlisting}
10.0.0.1:44992 -> 10.0.0.2:9000 [SYN]
wscale values seen: [0, 10]

10.0.0.2:9000 -> 10.0.0.1:44992 [SYN-ACK]
wscale values seen: [10]

996 anomalously small effective windows
\end{lstlisting}

\subsection{What We Learned}

The main prediction was correct.

One interesting observation was the very large number of packets.
An early uncapped capture contained more than 1.3 million packets
for a single 20 MB transfer.

This makes sense because the effective window became approximately
63 bytes. The transfer therefore required a very large number of
small data segments and acknowledgements. Since the attacker was
between the two endpoints, each packet also crossed the bridge twice.

Another observation was that the server's congestion window stayed
around 10 segments. The connection was receive-window-limited, so
congestion control did not have much opportunity to increase the
congestion window.

\section{Attack 2: Inflate}

\subsection{Idea}

The inflate attack is the opposite of deflate.

Instead of reducing the Window Scale, we increase it to 14.

For example, if the real scale is 10 but the server sees 14, the
server thinks the client's window is

\[
2^{14-10}=16
\]

times larger than it really is.

If the client's real receive buffer is small, the server may send
more data than the client can actually hold. This can lead to
retransmissions and stalls.

\subsection{Inflate Attack Diagram}

\begin{figure}[h]
\centering
\begin{tikzpicture}[node distance=1.5cm and 1.4cm]

\node[box] (client) {Client\\Real WScale = 10};
\node[box,right=2.6cm of client] (attacker) {Attacker\\Changes 10 $\rightarrow$ 14};
\node[box,right=2.6cm of attacker] (server) {Server\\Sees WScale = 14};

\draw[arrow] (client) -- node[above,align=center,font=\footnotesize]{SYN\\WScale = 10} (attacker);
\draw[arrow] (attacker) -- node[above,align=center,font=\footnotesize]{Modified SYN\\WScale = 14} (server);

\node[smallbox,below=1.6cm of client] (buffer)
{Real receive buffer\\can be small};

\node[smallbox,below=1.6cm of server] (belief)
{Server believes\\window is much larger};

\draw[dashedarrow] (client) -- (buffer);
\draw[dashedarrow] (server) -- (belief);

\end{tikzpicture}
\caption{Inflate attack: the server is given an inflated Window Scale}
\end{figure}

\subsection{Attack Process}

The same MITM and NFQUEUE pipeline used in the deflate attack was used.

The main change was:

\needspace{7\baselineskip}
\begin{lstlisting}
--new-shift 14
\end{lstlisting}

The first experiment used the normal Linux receive-buffer behaviour.

After that experiment showed almost no effect, the client's receive
buffer was fixed at 65536 bytes:

\needspace{7\baselineskip}
\begin{lstlisting}
throughput/bulk_client.py --rcvbuf 65536
\end{lstlisting}

This prevented Linux from automatically increasing the receive buffer.

\subsection{Expected Result}

We expected the server to believe that the client's receive window
was much larger than its real buffer.

This should cause the sender to transmit too much data, resulting in
retransmissions and possibly stalls.

\subsection{First Attempt}

The Window Scale rewrite was successful:

\needspace{7\baselineskip}
\begin{lstlisting}
shift 10 -> 14
\end{lstlisting}

However, there was almost no negative effect.

Throughput changed from:

\[
1176.326\ \text{MB/s}
\]

to:

\[
2480.288\ \text{MB/s}
\]

and retransmissions remained at zero.

So, the first attempt did not match our prediction.

\subsection{Why the First Attempt Failed}

The main reason was the lab environment.

The network was extremely fast and had almost no delay. Linux also
used receive-buffer autotuning and increased the client's real buffer
quickly.

The entire 20 MB transfer finished in less than a second. Therefore,
the server's false window was not large enough, for long enough, to
create a visible problem.

To make the attack effect easier to observe, we fixed the client's
receive buffer at 65536 bytes.

\subsection{Second Attempt}

After fixing the receive buffer, the attack produced the expected
effect.

\begin{table}[h]
\centering
\begin{tabular}{lrrrrl}
\toprule
Run & Throughput & Retrans. & cwnd & Rewrite & Real Shift \\
\midrule
1st & 47.354 MB/s & 306  & 156 & 10$\to$14 & 10 \\
2nd & 22.747 MB/s & 1065 & 121 & 10$\to$14 & 10 \\
3rd & 13.535 MB/s & 1398 & 167 & 1$\to$14 & 1 \\
\bottomrule
\end{tabular}
\caption{Inflate attack with a fixed receive buffer}
\end{table}

The third run also showed:

\needspace{12\baselineskip}
\begin{lstlisting}
10.0.0.1:59258 -> 10.0.0.2:9000 [SYN]
wscale values seen: [1, 14]

advertised_window=0
wscale=14
effective=0 bytes
\end{lstlisting}

\subsection{Another Observation}

The real Window Scale changed from 10 to 1 between repeated runs.

This happened because Linux can keep TCP metrics for previously used
destinations. Earlier degraded connections affected the parameters
chosen for later connections.

As a result, the difference between the real and fake scale became:

\[
2^{14-10}=16
\]

in one run and:

\[
2^{14-1}=8192
\]

in another run.

This explains why the retransmissions increased from 306 to 1065
and then to 1398.

\subsection{What We Learned}

The inflate attack is more dependent on the endpoint's TCP behaviour
than the deflate attack.

In our lab, the attack was not clearly visible until the client's
receive buffer was explicitly limited.

This is an important experimental finding: the attack itself can be
implemented correctly, but the final effect depends on factors such
as receive-buffer autotuning, network speed, and TCP metrics.

\section{Attack 3: Slow Read / Zero-Window DoS}

\subsection{Idea}

The Slow Read attack works differently.

It does not modify packets or use ARP spoofing.

Instead, the attacker opens many connections and reads the response
very slowly. Each connection uses a very small receive buffer.

In this experiment, the server had a worker pool of only 20
connections.

\subsection{Slow Read Attack Diagram}

\centering
\begin{tikzpicture}[node distance=1.2cm and 1.2cm]

{Connection 1};
\node[smallbox,below=1.4cm of attacker] (c2)
{Connection 2};
\node[smallbox,below right=1.4cm and 0.7cm of attacker] (c3)
{Connection 3};
\node[below=0.3cm of c2] (dots) {$\vdots$};
\node[smallbox,below=1.4cm of dots] (c50)
{Connection 50};

\node[box,right=5.0cm of attacker] (server)
{HTTP Server\\20 workers};

\draw[arrow] (c1) -- (server);
\draw[arrow] (c2) -- (server);
\draw[arrow] (c3) -- (server);
\draw[arrow] (c50) -- (server);

\node[smallbox,below=1.3cm of server] (pool)
{20 workers occupied\\

\draw[dashedarrow] (server) -- (pool);

\node[smallbox,right=of pool] (health)
{Legitimate\\/\texttt{health}\\request fails};

\draw[dashedarrow] (pool) -- (health);

\end{tikzpicture}
\caption{Slow Read attack and connection-pool exhaustion}
\end{figure}

\subsection{Attack Process}

The server was started with:

\needspace{7\baselineskip}
\begin{lstlisting}
--max-conns 20
\end{lstlisting}

The attacker then:

\begin{itemize}
    \item opened 50 connections,
    \item requested \texttt{/bigfile},
    \item used an 8-byte receive buffer,
    \item read only a few bytes every second,
    \item kept the connections open for 30 seconds.
\end{itemize}

The server also provided a \texttt{/health} endpoint so that we could
test whether a normal client could still access the server.

\subsection{Expected Result}

There were 50 attack connections but only 20 available worker slots.

Therefore, we expected the worker pool to become full and legitimate
requests to fail or stall during the attack.

After the attack connections closed, the server should recover.

\subsection{Actual Result}

The results were:

\needspace{17\baselineskip}
\begin{lstlisting}
Baseline health check
-> ok=True rtt=0.001s

Health check during attack
-> ok=False rtt=3.000s
   Connection reset by peer

20/50 connections held open

Health check after attack
-> ok=True rtt=0.001s
\end{lstlisting}

Exactly 20 connections stayed open for the full 30 seconds.

The other 30 connections were rejected or reset because the worker
pool was already full.

The health check failed during the attack and immediately recovered
after the connections were released.

\subsection{Result}

The result matched our prediction.

This attack was more predictable than the inflate attack because it
did not depend on Window Scale manipulation or receive-buffer
autotuning. It only required the server to have a limited resource
per connection.

\subsection{Defense A: Static ARP Entries}

\subsubsection*{How It Works}

The attack starts with ARP poisoning.

Static ARP entries prevent the attacker from changing the client and
server's ARP mappings.

The script:

\needspace{7\baselineskip}
\begin{lstlisting}
defense/harden_arp.sh
\end{lstlisting}

reads the real MAC addresses and creates permanent neighbour-table
entries.

\begin{figure}[h]
\centering
\begin{tikzpicture}[node distance=1.6cm]

\node[box] (client) {Client};
\node[box,right=3.5cm of client] (server) {Server};
\node[box,below=1.7cm of $(client)!0.5!(server)$] (attacker)
{Attacker};

\draw[arrow] (client) -- node[above]{Normal ARP mapping} (server);
\draw[dashedarrow] (attacker) -- node[left,align=center,font=\footnotesize]
{Forged ARP\\reply blocked} (client);
\draw[dashedarrow] (attacker) -- node[right,align=center,font=\footnotesize]
{Forged ARP\\reply blocked} (server);

\node[smallbox,below=1.4cm of attacker]
{No MITM position};

\end{tikzpicture}
\caption{Static ARP prevents the attacker from becoming MITM}
\end{figure}

\subsubsection*{Expected Result}

The forged ARP replies should be ignored.

Therefore:

\begin{itemize}
    \item the attacker should not become MITM,
    \item no packets should reach the attacker's rewrite script,
    \item no Window Scale should be changed,
    \item throughput should remain close to baseline.
\end{itemize}

\subsubsection*{Actual Result}

The rewrite program started, but it did not rewrite any packet:

\needspace{8\baselineskip}
\begin{lstlisting}
2026-09-19 02:01:56,938 listening on NFQUEUE 0
(no further lines -- zero rewrites)
\end{lstlisting}

The packet capture showed:

\needspace{13\baselineskip}
\begin{lstlisting}
10.0.0.1:53470 -> 10.0.0.2:9000 [SYN]
wscale values seen: [10]

10.0.0.2:9000 -> 10.0.0.1:53470 [SYN-ACK]
wscale values seen: [10]

0 flow(s) with a WScale mismatch
\end{lstlisting}

The transfer also completed normally:

\needspace{14\baselineskip}
\begin{lstlisting}
server: throughput=2196.388 MB/s
total_retrans=0
snd_wscale=10

client: throughput=1827.000 MB/s
total_retrans=0
snd_wscale=10
rcv_wscale=10
\end{lstlisting}

\subsubsection*{Conclusion}

The defense worked as expected.

The attacker could not obtain the MITM position, so the later
Window Scale modification step could not happen.

% ============================================================
\subsection{Defense B: IPsec AH}

\subsubsection*{How It Works}

IPsec Authentication Header (AH) was configured in transport mode.

The setup used Linux's \texttt{ip xfrm} interface and a manually
configured shared HMAC-SHA1-96 key.

AH provides integrity protection for the IP packet, including the
TCP header.

\begin{figure}[h]
\centering
\begin{tikzpicture}[node distance=1.5cm and 1.3cm]

\node[box] (client) {Client\\IPsec AH};
\node[box,right=2.4cm of client] (attacker) {Attacker};
\node[box,right=2.4cm of attacker] (server) {Server\\IPsec AH};

\draw[arrow] (client) -- node[above,align=center,font=\footnotesize]
{AH-protected\\traffic} (attacker);
\draw[arrow] (attacker) -- node[above,align=center,font=\footnotesize]
{Forwarded\\traffic} (server);

\node[smallbox,below=1.5cm of attacker] (nomod)
{Cannot modify\\AH-protected data};

\draw[dashedarrow] (attacker) -- (nomod);

\end{tikzpicture}
\caption{IPsec AH protects packet integrity}
\end{figure}

The configuration was applied using:

\needspace{7\baselineskip}
\begin{lstlisting}
defense/setup_ipsec_ah.sh
\end{lstlisting}

Static ARP protection was not enabled for this experiment, so the
attacker could still remain on-path.

\subsubsection*{Expected Result}

We expected the attacker to be unable to modify the protected packet.

Two possible outcomes were considered:

\begin{enumerate}
    \item The modified packet could fail AH verification and be dropped.
    \item The attacker's TCP-specific NFQUEUE rule could stop matching
    because AH changes the IP protocol from TCP (6) to AH (51).
\end{enumerate}

In either case, the Window Scale should not be modified.

\subsubsection*{Actual Result}

The IPsec configuration was installed successfully.

However, the attacker logged zero rewrites:

\needspace{8\baselineskip}
\begin{lstlisting}
2026-09-19 02:23:40,801 listening on NFQUEUE 0
(no further lines -- zero rewrites)
\end{lstlisting}

The detector found no SYN packets in the capture:

\needspace{10\baselineskip}
\begin{lstlisting}
=== SYN / SYN-ACK WScale values per flow ===
(empty)

0 flow(s) with a WScale mismatch
\end{lstlisting}

The transfer completed successfully:

\needspace{13\baselineskip}
\begin{lstlisting}
server: throughput=158.140 MB/s
total_retrans=202
snd_wscale=10

client: throughput=156.081 MB/s
total_retrans=0
snd_wscale=10
\end{lstlisting}

\subsubsection*{Why the Result Was Different from the Prediction}

The connection did not time out.

Instead, the second expected outcome happened: the attacker's
TCP-based NFQUEUE rule did not match the AH-wrapped packets.

Therefore, the attacker's rewrite program never received the packets.

The Window Scale remained unchanged.

The lower throughput and retransmissions observed during this run
were associated with the heavy workload on the single physical
machine. The capture reported 5,587 dropped packets from its own
kernel buffer while around 9,000 packets were received.

Importantly, this experiment did not directly test AH's cryptographic
rejection of a modified packet. The attacker never reached the point
where it could modify the AH-protected packet.

\subsubsection*{Conclusion}

IPsec AH prevented the Window Scale tampering in this experiment.
The exact mechanism was that the attacker's TCP packet filter did not
match the AH-wrapped traffic.

\section{Assumptions}

The experiments depend on several assumptions.

\begin{enumerate}
    \item \textbf{The attacker is on-path.}
    The attacker must be on the same Layer-2 network as the client
    and server. ARP spoofing is assumed to be possible.

    \item \textbf{There is no transport-layer integrity protection.}
    The Window Scale attack assumes that TCP headers are not protected
    by IPsec AH, ESP, or another integrity mechanism.

    \item \textbf{The attacker uses one network interface.}
    The attacker relies on Linux IP forwarding and ARP resolution
    to relay packets.

    \item \textbf{Window Scale is negotiated during the handshake.}
    The attack depends on the scale value being selected during the
    SYN/SYN-ACK exchange and not being re-checked later.

    \item \textbf{Both endpoints support Window Scale.}
    If Window Scale is not used, the normal 64 KB TCP window is used
    and there is no scale value to modify.

    \item \textbf{Linux TCP behaviour can change between runs.}
    Receive-buffer autotuning and TCP metrics caching affected the
    inflate experiment.

    \item \textbf{The lab is much faster than a normal network.}
    The experiments used namespaces and a software bridge on one
    physical machine. Therefore, the exact throughput and timing
    should not be treated as real-WAN measurements.

    \item \textbf{Only the client's SYN was modified.}
    The experiments used the \texttt{client-syn} target. The software
    also supports other targets, but they were not used here.

    \item \textbf{Slow Read requires a limited server resource.}
    The Slow Read attack worked because the server had a fixed
    20-connection worker pool.

    \item \textbf{Static ARP requires trusted MAC addresses.}
    The correct MAC addresses must be known before the attacker
    successfully poisons the ARP cache.

    \item \textbf{The IPsec experiment used a manual shared key.}
    This demonstrates the integrity mechanism, not a complete
    production key-management system. A real deployment would normally
    use IKE for key negotiation and rotation.

    \item \textbf{The IDS is detection-only.}
    The live detector reports suspicious traffic but does not
    automatically block or rate-limit it.
\end{enumerate}

\section{Conclusion}

This project demonstrated three different TCP-based denial-of-service
scenarios in a controlled Linux lab.

The deflate attack showed that changing the Window Scale from 10 to 0
can make the server severely underestimate the client's receive window.
In our experiment, throughput fell from 1781.163 MB/s to 2.314 MB/s,
a reduction of about 99.9\%, while retransmissions remained at zero.

The inflate attack showed a different behaviour. Increasing the
Window Scale did not immediately produce an effect because Linux
automatically increased the client's receive buffer. After the
receive buffer was fixed at 65536 bytes, the expected retransmissions
appeared.

The Slow Read attack was simpler and more predictable. With a server
limited to 20 worker connections, 20 slow connections were enough to
exhaust the available pool and make the health endpoint unavailable
during the attack.

We also tested three defenses. Static ARP prevented the attacker from
obtaining the MITM position. IPsec AH prevented the attacker's packet
modification pipeline from operating on the protected traffic. The
live IDS detected the Window Scale mismatch.

An important part of this project was comparing expected results with
actual results. The inflate experiment showed that an attack can be
implemented correctly but still produce little visible damage when
the environment has different TCP buffering and timing behaviour.
This makes controlled testing and measurement important when studying
TCP attacks.
